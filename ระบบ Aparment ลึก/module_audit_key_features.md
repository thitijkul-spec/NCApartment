# สเปค Module: ประวัติการใช้งาน (Audit Log)

อ้างอิงข้อมูลจากทุก module ที่มี action สำคัญ (ดูหัวข้อ 5)

สถานะ: ✅ สเปคเสร็จ (รอ confirm ก่อน implement)

---

## 1. หน้าที่ของโมดูล

หน้ากลางแสดงประวัติการกระทำ "สำคัญ" ที่เกิดขึ้นในระบบทั้งหมดของสาขานี้ — ใครทำอะไร เมื่อไหร่ กับข้อมูลไหน เพื่อให้เจ้าของอาคารตรวจสอบย้อนหลังได้ว่ามีการเปลี่ยนแปลงข้อมูลสำคัญ (สร้าง/ลบ/เงิน/เปลี่ยนสถานะ) เกิดขึ้นบ้าง — **ไม่ใช่ full audit trail ที่บันทึกทุก field ที่แก้ไข**

**ขอบเขต multi-building:** ทุกอย่างในหน้านี้กรองตาม `building_id` ที่กำลังเลือกอยู่

**ไม่ใช่สโคปของโมดูลนี้:**
- ไม่มีมุมมองย่อยผูกกับ entity เฉพาะ (เช่น tab "ประวัติ" ในห้อง/ผู้เช่า) — มีแค่หน้ากลางอย่างเดียว มีคนละหน้า
- ไม่มีปุ่ม export Excel/PDF — ดูในระบบอย่างเดียว
- ไม่มีการคลิกดูรายละเอียดเพิ่มเติม — แต่ละแถวเป็น static row จบในตัว
- ไม่มี auto-purge — เก็บ log ไว้ถาวร (ยังไม่ต้องคิดเรื่อง retention policy ตอนนี้)
- ไม่ log ทุก create/update/delete ของทุก module — เฉพาะ action สำคัญเท่านั้น (ดูหัวข้อ 5)

## 2. Data Model

```
AuditLog
- id
- building_id            → FK Building
- actor_type              → enum: user | system
- actor_user_id           → FK User, nullable (null ถ้า actor_type = system)
- actor_name_snapshot      → string — ชื่อที่แสดงตอนนั้น (เช่น "Tanjai Thiti" หรือชื่อ system actor ตายตัวเช่น "Auto checkout", "ระบบ (ริบเงินมัดจำ)")
- action_type             → enum: create | delete | payment | status_change
- module_tag              → string — ป้ายกำกับ module ที่แสดงในการ์ด (เช่น "ใบแจ้งหนี้", "ผู้เช่า", "ตั้งค่า", "พัสดุ", "แจ้งซ่อม", "มัดจำ", "สัญญา", "ห้องพัก", "จองห้อง", "ค่าใช้จ่าย", "รายได้อื่นๆ", "ฐานข้อมูลบัญชี")
- entity_type             → string — ชื่อ entity ที่ถูกกระทำ (เช่น "Bill", "Tenant", "Account", "Parcel")
- entity_id               → string/int — FK ไปยัง record ต้นทาง (ไม่ enforce FK จริงในระดับ DB เพราะ entity_type เปลี่ยนไปตามแถว)
- entity_label            → string — ป้ายอ้างอิงที่มนุษย์อ่านได้ (เช่น "CINV-5E43E550", ชื่อผู้เช่า, เลขห้อง)
- description             → string — ข้อความเต็มที่แสดงในการ์ด (generate ตอนบันทึก เช่น "บันทึกชำระเงินใบแจ้งหนี้ CINV-5E43E550")
- old_value               → JSON, nullable — snapshot ข้อมูลก่อนแก้ไข (เก็บไว้เผื่ออนาคต **ยังไม่แสดงในหน้าจอตอนนี้**)
- new_value               → JSON, nullable — snapshot ข้อมูลหลังแก้ไข (เก็บไว้เผื่ออนาคต **ยังไม่แสดงในหน้าจอตอนนี้**)
- created_at
```

**หมายเหตุ:** `old_value`/`new_value` เก็บไว้ล่วงหน้าสำหรับ feature ในอนาคต (เช่น เปิด modal ดู diff) แต่รอบนี้ backend เขียนแค่ให้ครบ ไม่ต้องมี UI แสดงผล

## 3. หน้าจอย่อย

### 3.1 หน้าหลัก "ประวัติการใช้งาน"
- Header: "ประวัติการใช้งาน" + subtitle "ดูประวัติการจัดการข้อมูลทั้งหมดของสาขานี้"
- Stat cards (3 ใบ):
  - **วันนี้** — จำนวนรายการ log ที่เกิดวันนี้
  - **7 วันล่าสุด** — จำนวนรายการ log ใน 7 วันที่ผ่านมา (รวมวันนี้)
  - **ผู้ใช้งาน Active** — รายชื่อ actor (avatar + ชื่อ + จำนวนครั้งที่ทำ action) **นับเฉพาะวันนี้เท่านั้น** เรียงจากทำมากไปน้อย รวม system actor ด้วย (เช่น "Auto checkout")
- ช่องค้นหา "ค้นหาประวัติ..." — ค้นจาก `description` / `entity_label` / `actor_name_snapshot`
- Filter (กรองได้ 2 แบบพร้อมกัน):
  - Dropdown กรองตาม **module** (ตาม `module_tag`)
  - Dropdown กรองตาม **ประเภท action** (สร้าง/ลบ/เงิน/เปลี่ยนสถานะ)
- รายการ log จัดกลุ่มตามวันที่ (section header แบบ "16 สิงหาคม 2569") เรียงใหม่สุดอยู่บน
- แต่ละแถว (static row ไม่มี interaction คลิก): ไอคอนวงกลมสี (สีตาม `action_type` — เขียว=create, แดง=delete, ฟ้า=payment, เขียวอมฟ้า=status_change), ข้อความ `description`, ชื่อ actor + module_tag + เวลาแบบ relative (เช่น "35 นาทีที่แล้ว", เกิน 24 ชม. แสดงเป็นชั่วโมง/วันตามความเหมาะสม)
- ไม่มีปุ่ม export

## 4. Permission

- **ดูได้เฉพาะ owner เท่านั้น** — staff ไม่เห็นเมนู/หน้านี้เลย ไม่ว่าจะมี permission โมดูลอื่นแบบไหนก็ตาม (ไม่ต้องมี permission toggle แยกในหน้าตั้งค่า)

## 5. ขอบเขต Action ที่ต้อง Log

**หลักการ:** log เฉพาะ action สำคัญ 4 ประเภท (`create` / `delete` / `payment` / `status_change`) ของ entity หลักในแต่ละ module — **ไม่ log การแก้ไขข้อมูลทั่วไป (update field ปลีกย่อย)**

| Module (`module_tag`) | Action ที่ log |
|---|---|
| ห้องพัก | สร้างห้อง, ลบห้อง, เปลี่ยนสถานะห้อง (ว่าง/มีผู้เช่า/ปิดปรับปรุง ฯลฯ) |
| จองห้อง | สร้างการจอง, ยกเลิกการจอง, **auto checkout** (ระบบเปลี่ยนสถานะเองเมื่อจองหมดช่วงเวลา — actor แบบ system ชื่อ "Auto checkout") |
| ผู้เช่า | เพิ่มผู้เช่า, ลบผู้เช่า, มอบหมาย/ย้ายห้องให้ผู้เช่า |
| เอกสารสัญญา | สร้างสัญญา, ยกเลิก/สิ้นสุดสัญญา |
| ใบแจ้งหนี้ (บิล) | สร้างบิล (รวมบิลกำหนดเอง), ลบบิล, บันทึกชำระเงิน |
| แจ้งซ่อม | สร้างงานแจ้งซ่อม, ลบงาน, เปลี่ยนสถานะงาน |
| พัสดุ | บันทึกพัสดุเข้า, ลบพัสดุ, เปลี่ยนสถานะพัสดุ |
| ค่าใช้จ่าย | สร้างรายการ, ลบรายการ, บันทึกจ่ายเงิน |
| รายได้อื่นๆ | สร้างรายการ, ลบรายการ, บันทึกรับเงิน |
| มัดจำ | คืนเงินมัดจำ, **ริบเงินมัดจำ** (ระบบสร้าง OtherIncome อัตโนมัติ — actor แบบ system ชื่อ "ระบบ (ริบเงินมัดจำ)") |
| ฐานข้อมูลบัญชี | เพิ่ม/ลบบัญชี (Account) |
| ตั้งค่า | เพิ่ม/ลบ user, เพิ่ม/ลบบัญชีรับเงิน, แก้ไขข้อมูลกิจการ (นับเป็น update แต่ถือว่าสำคัญพอที่จะ log เพราะกระทบเอกสารทางการเงิน) |

**Auto-action ที่ log ด้วย system actor (ชื่อ actor ตายตัวต่อประเภท ไม่ใช่ user จริง):**
- `Auto checkout` — ห้อง/การจองหมดช่วงเวลาที่กำหนด ระบบเปลี่ยนสถานะเอง
- `ระบบ (ริบเงินมัดจำ)` — ริบเงินมัดจำแล้วสร้าง OtherIncome หมวด "เงินมัดจำริบ" อัตโนมัติ

**ที่ตั้งใจไม่แยก log ต่างหาก (เป็น side-effect ของ action ที่ log อยู่แล้ว):**
- ออกใบเสร็จ/ใบกำกับภาษีอัตโนมัติตอนชำระเงิน — รวมอยู่ใน log "บันทึกชำระเงิน" ของบิลนั้นแล้ว ไม่ต้องมีแถวแยก
- สร้าง `LedgerEntry` อัตโนมัติ (ทุกครั้งที่มีเงินเข้า-ออกจริง) — เป็น derived record ภายใน ไม่ต้องมีแถวแยก

## 6. ความสัมพันธ์กับ module อื่น

- **ทุก module ที่มี action สำคัญตามตารางหัวข้อ 5** ต้องเรียกเขียน `AuditLog` ตอน action นั้นสำเร็จ (เป็นความรับผิดชอบของ backend logic แต่ละ module ไม่ใช่ trigger ระดับ DB)
- **ตั้งค่า:** ไม่มี permission toggle สำหรับโมดูลนี้ (owner-only แบบ hardcode)
- **ห้องพัก:** Tab "ประวัติ" ที่เคยพักไว้ใน Room Detail Modal (`module_room_key_features.md`) **ยังไม่เชื่อมกับโมดูลนี้ในรอบนี้** — ตัดออกจากสโคป เพราะโมดูลนี้มีแค่หน้ากลางอย่างเดียว (ดูหมายเหตุท้ายไฟล์)
