# Prompt สำหรับแชทใหม่ — ต่อจาก module "ประวัติการใช้งาน" (การเงิน, รายงาน, ตั้งค่า, ประวัติการใช้งาน เสร็จครบหมดแล้ว)

คัดลอกทั้งหมดด้านล่างนี้ไปวางเป็นข้อความแรกในแชทใหม่ แล้วแนบภาพแคปหน้าจอของ module ที่จะทำต่อ (รอบนี้เลือกทำ **"ภาพรวม" (Dashboard)** — **module สุดท้ายที่เหลือในระบบ**) — ถ้าไม่มีภาพต้นแบบ บอกในแชทใหม่ได้เลยว่าจะให้ออกแบบเอง (module นี้ต้องรวมข้อมูลจากแทบทุก module ที่ทำเสร็จแล้ว — ดูหมายเหตุท้ายไฟล์)

---

ฉันกำลังพัฒนา **ระบบจัดการอพาร์ตเมนต์** โดยอ้างอิงจากโปรแกรมต้นแบบที่มีอยู่แล้ว เป้าหมายคือทำให้ฟังก์ชันการทำงานและหน้าตาใกล้เคียงต้นแบบก่อน ส่วนฟีเจอร์เพิ่มเติมจะทำทีหลัง

**วิธีทำงาน:** ฉันทำทีละ module แยกกันคนละแชท เพื่อไม่ให้ context ปนกัน

**สิ่งที่ต้องการจากคุณในแชทนี้:**
1. ดูภาพแคปหน้าจอที่แนบมา (module: **ภาพรวม (Dashboard)**) — ถ้าไม่มีภาพ ให้ถามความต้องการแล้วออกแบบเองได้เลย
2. วิเคราะห์โครงสร้างหน้าจอ: layout, ฟิลด์ข้อมูล, ปุ่ม/action, ตาราง, filter/search, validation
3. สรุปเป็น **prompt/สเปค** สำหรับสร้างโค้ดจริง ครอบคลุม: ชื่อ/หน้าที่ module, Data model, หน้าจอย่อย, Action/ฟังก์ชัน, ความสัมพันธ์กับ module อื่น — แยกไฟล์สเปคคนละไฟล์ต่อ module ถ้าทำหลาย module พร้อมกัน
4. **ถามฉันให้ละเอียด/ครบก่อนเสมอ** (ทีละ 4 ข้อ เพราะเครื่องมือจำกัด) ก่อนสรุปสเปคจบ — อย่าเดาเอง ถ้าจุดไหนไม่ชัดจากภาพให้ถาม
5. หลังสรุปสเปคแล้ว รอฉัน confirm ก่อนค่อยเริ่ม implement โค้ดจริง — **อย่าเพิ่งลงมือเขียนโค้ดจนกว่าฉันจะบอกให้เริ่ม** แม้จะดูเหมือนพร้อมแล้วก็ตาม

**Tech stack:** Next.js 14 (App Router) + Prisma + SQLite — ตัดสินใจแล้วจากงานก่อนหน้า อยู่ที่ `D:\ระบบ อพาร์มเม้นท์\code`

**โฟลเดอร์เก็บสเปค/เอกสารวางแผน (ไม่ใช่โค้ด):** `D:\ระบบ อพาร์มเม้นท์\code\ระบบ Aparment ลึก` (โฟลเดอร์ย่อยชื่อ "ระบบ Aparment ลึก" ที่อยู่**ข้างใน**โฟลเดอร์โค้ด `D:\ระบบ อพาร์มเม้นท์\code` — ไม่ใช่ `D:\ระบบ Aparment ลึก` ที่ root ของ D: ซึ่งเป็นคนละโฟลเดอร์ ไม่ได้ใช้งานแล้ว/ไม่มี git tracking) — ให้เซฟไฟล์สรุปสเปค (`module_xxx_key_features.md`) และไฟล์ prompt แชทถัดไปไว้ที่นี่เสมอ **อย่าเซฟเอกสารสเปคไว้ในโฟลเดอร์โค้ดส่วนอื่น** (`D:\ระบบ อพาร์มเม้นท์\code\docs` มีเอกสารเก่าที่ล้าสมัย/ผิดสเปคอยู่ — อย่ายึดเป็นหลัก)

**รายการ Module ทั้งหมด:**
1. ภาพรวม (Dashboard)
2. ห้องพัก (ห้องพัก ✅ สเปคเสร็จ, จองห้อง ✅ สเปคเสร็จ, มิเตอร์น้ำ-ไฟ ✅ สเปคเสร็จ) — **ยังไม่ implement โค้ดจริงเลยสักตัว รอทำพร้อมกันทีหลัง**
3. ผู้เช่า (ผู้เช่า ✅ สเปคเสร็จ, เอกสารสัญญา ✅ สเปคเสร็จ) — **ครบทุกตัวในหมวดนี้แล้ว**
4. **การเงิน** ✅ **ครบทุกตัวในหมวดนี้แล้ว** (บิลรายเดือน, ใบเสร็จ/ใบกำกับภาษี [ออกแบบเองไม่ได้อิงภาพต้นแบบ — แก้ทีหลังได้], รายได้อื่นๆ, ค่าใช้จ่าย [ทั้งคู่ออกแบบเป็นระบบบัญชีย่อย มี Contact/Account/VAT/WHT/LedgerEntry — ไม่ได้ mirror ภาพต้นแบบตรงๆ], ฐานข้อมูลบัญชี [4 แท็บ: ทะเบียนเอกสาร/บัญชีแยกประเภท/จัดการบัญชี/ยอดค้างชำระ-ค้างรับ; generalize BankAccount → Account; เพิ่ม Deposit tracking ผูก module_contract; ตัด Bank Statement PDF cross-check ออกจากสโคป])
5. **งานซ่อมบำรุง (แจ้งซ่อม)** ✅ สเปคเสร็จ — [แยกหมวดต่างหาก ไม่รวมกับพัสดุ] รวม sub-feature "งานซ่อมบำรุง" (ล้างแอร์/อุปกรณ์ส่วนกลาง)
6. **พัสดุ** ✅ สเปคเสร็จ — [แยกหมวดต่างหาก ไม่รวมกับแจ้งซ่อม]
7. **ประวัติการใช้งาน (Audit Log)** ✅ สเปคเสร็จ — หน้ากลางอย่างเดียว owner-only, log เฉพาะ action สำคัญ (สร้าง/ลบ/เงิน/เปลี่ยนสถานะ)
8. **ตั้งค่า** ✅ สเปคเสร็จ — sidebar 7 หัวข้อ (ข้อมูลกิจการ/ผู้รับเงิน, ค่าตั้งสาขา, ผู้ใช้งาน/สิทธิ์, ช่าง, ประเภทงานซ่อม, Template สัญญา, LINE OA) + หน้า Building Selector แยกต่างหาก
9. **รายงาน (Reports — export Excel/PDF)** ✅ สเปคเสร็จ — 4 หมวด 17 รายงาน (การเงิน 6, ห้องพัก 5, ซ่อมบำรุง/พัสดุ 3, ผู้เช่า 3)
10. **ภาพรวม (Dashboard)** ✅ สเปคเสร็จ — stat cards + กราฟ (recharts) + รายการติดตาม + activity feed (owner only), ไม่ real-time, quick action reuse modal เดิม, ไม่มีมุมมองรวมหลายอาคาร

**✅ ครบทุก module ในสโคปแล้ว — ไม่มี module ค้างเหลืออีก** ขั้นตอนถัดไปของโปรเจกต์คือเริ่ม **implement โค้ดจริง** ตามสเปคทั้งหมด (ไม่ใช่การออกแบบสเปคโมดูลใหม่แล้ว) — ดูหัวข้อ "ข้อจำกัดสำคัญก่อน implement จริง" ใน `module_dashboard_key_features.md` เรื่องลำดับการเริ่ม implement เพราะยังไม่มี module ไหนมีโค้ดจริงเลย

## [สำคัญ — สถาปัตยกรรมระดับระบบ] รองรับหลายอาคาร/สาขา (Multi-Building) ตั้งแต่แรก
- ระบบต้องรองรับเจ้าของที่มีมากกว่า 1 อาคาร/อพาร์ตเมนต์ ภายใต้บัญชีเดียวกัน
- ทุก entity ที่เกี่ยวกับห้อง (ห้อง, ชั้น, ผู้เช่า, บิล, ค่าตั้งสาขา ฯลฯ) ผูกกับ `building_id`
- ไม่แสดงหลายอาคารในหน้าเดียวกัน — ทุกหน้าจอแสดงเฉพาะอาคารที่กำลังเลือกอยู่
- การสลับอาคารทำงานเหมือน "สลับโปรไฟล์/workspace switcher" — เลือกตอน login ครั้งแรก และสลับได้จากหน้า "ตั้งค่า"
- เลขห้อง unique เฉพาะภายในอาคารเดียวกัน ไม่ unique ทั้งระบบ

## ⚠️ สถานะโค้ดจริงในโปรเจกต์ (สำคัญ อ่านก่อนเริ่ม)
โค้ดที่มีอยู่แล้ว (`app/rooms`, `app/bookings`, `prisma/schema.prisma`) เป็นเวอร์ชันเก่ากว่าที่ตัดสินใจไว้ในสเปคทุกไฟล์ในโฟลเดอร์นี้มาก (status ห้องมีแค่ 3 ค่า, ไม่มี multi-building, ไม่มี Gantt, Booking รองรับแค่รายวัน, ไม่มี meter reading) — **ยังไม่ได้ implement โค้ดจริงเลยสักโมดูล มีแต่สเปค** ถ้า module ใหม่อ้างอิงข้อมูลห้อง/ผู้เช่า ให้อิงตามไฟล์สเปคในโฟลเดอร์นี้ ไม่ใช่โค้ดปัจจุบันในโปรเจกต์

โค้ดต้นแบบเก่ามี `model User` ใน `prisma/schema.prisma` (role: `owner`/`staff` + `permissions` เป็น list รหัสโมดูล) ที่ module_expense/module_other_income อ้างอิงไว้สำหรับสิทธิ์การเข้าถึง — ระบบจัดการ user/role จริงจะไปทำใน module "ตั้งค่า" ทีหลัง ไม่ใช่ในแชทนี้

## ลิงก์สเปคที่ทำเสร็จแล้ว (อ่านเพิ่มถ้าต้องอ้างอิง)
- `module_room_key_features.md` — ห้องพัก: สถานะห้อง, การคิดค่าน้ำ-ไฟ-เน็ต-ส่วนกลางต่อห้อง, Calendar/Gantt view, มี Tab "แจ้งซ่อม" ใน Room Detail Modal — เป็น data source เดียวกับ `module_repair`
- `module_booking_key_features.md` — จองห้อง
- `module_meter_key_features.md` — มิเตอร์น้ำ-ไฟ
- `module_tenant_key_features.md` — ผู้เช่า: ข้อมูลผู้เช่า, โครงสร้าง `room_occupancies` แยกจาก `tenants`, Flow เชื่อมต่อ LINE 2 วิธี — ใช้โดย `module_repair` (แจ้งซ่อมผ่าน LIFF) และ `module_parcel` (แจ้งเตือนพัสดุผ่าน LINE)
- `module_contract_key_features.md` — เอกสารสัญญา
- `module_bill_key_features.md` — บิลรายเดือน: Bill/BillLineItem/Payment data model, สถานะ 6 แบบ (คำนวณ overdue แบบ computed สด ไม่มี cron), บิลรายเดือน/บิลแรกเข้า, split payment แบบกดเพิ่มทีละครั้ง, ใบเสร็จ/ใบกำกับภาษีแยกเลข running number จากเลขบิล, หน้า "ใบเสร็จ" แยกต่างหาก, ปริ้นบิล/ใบเสร็จ A5 (ใบกำกับภาษี A4 formal), ต่อสัญญาอัตโนมัติสร้างสัญญาใหม่ทุกครั้ง
- `module_repair_key_features.md` — แจ้งซ่อม: RepairRequest data model, ใช้ data source เดียวกับ Tab "แจ้งซ่อม" ใน Room Detail Modal, แจ้งซ่อมผ่าน LINE LIFF (auto-link ห้อง/ผู้เช่าจาก LINE ID), แจ้งเตือนงานใหม่ในภาพรวม, รายชื่อช่าง (Technician) จัดการในหน้า "ตั้งค่า", ลบงาน = hard delete, sub-feature เสริม "งานซ่อมบำรุง" (ล้างแอร์ผูกห้อง + อุปกรณ์ส่วนกลางผูก SharedEquipment, ไม่มีแจ้งเตือนอัตโนมัติ)
- `module_parcel_key_features.md` — พัสดุ: Parcel data model (ไม่มี field ประเภทพัสดุ, รูปใบนำส่งไม่บังคับ), สถานะ 3 ขั้น (พัสดุเข้า/แจ้งลูกบ้านแล้ว/รับพัสดุแล้ว) + "ตกค้าง" เป็น flag คำนวณสดจาก `parcel_overdue_days`, แจ้งเตือนผ่าน LINE แบบกดเอง (ไม่ auto), เปลี่ยนสถานะย้อนกลับได้มี confirm dialog, ลบพัสดุ = hard delete, ตัด OCR อ่านชื่อผู้รับออกจากสโคป
- `module_receipt_key_features.md` — ใบเสร็จ/ใบกำกับภาษี: **ออกแบบเองไม่ได้อิงภาพต้นแบบ (แก้ทีหลังได้)** ไม่มี data model แยก ต่อยอดจาก `Payment` ใน module_bill (เพิ่ม field `receipt_no`/`tax_invoice_no` แยก sequence กัน + snapshot ข้อมูลผู้รับเงิน), ใบเสร็จออกอัตโนมัติทุกครั้งที่ชำระ (A5), ใบกำกับภาษีเป็น toggle เสริม (A4 formal, ไม่คิด VAT เพราะค่าเช่าที่พักยกเว้นภาษีตามกฎหมาย), หน้ารายการแยกต่างหากในเมนูย่อยการเงิน ต้องรอ module "ตั้งค่า" ทำ field ข้อมูลกิจการ (ชื่อ/ที่อยู่/เลขผู้เสียภาษี) ให้ก่อนถึงจะ implement ได้ครบ
- `module_expense_key_features.md` — ค่าใช้จ่าย: **ออกแบบเองเป็นระบบบัญชีย่อย ไม่ได้ mirror ภาพต้นแบบตรงๆ** หัวบิล+รายการย่อยหลายบรรทัด (multi-line), VAT ต่อรายการย่อย (รวม/แยก/%ปรับได้ default 7), หัก ณ ที่จ่าย+เลขใบกำกับภาษีซื้อเก็บระดับหัวบิล (กรอกเองไม่คำนวณอัตโนมัติ), ซื้อสด/ซื้อเชื่อ+แบ่งจ่ายหลายงวดหลายวิธีหลายบัญชี (ExpensePayment), เลขที่เอกสาร `EXP-YYYY-MM-###` รันแยกต่ออาคาร รีเซ็ตรายเดือน, snapshot ข้อมูลผู้ขาย ณ เวลาบันทึก, แก้ไข/ลบได้อิสระไม่ล็อก, ผูก permission ระดับ module หมวด "การเงิน", มี `LedgerEntry` เตรียมไว้ (ยังไม่ทำ UI กระทบยอด — เก็บ requirement อัปโหลด PDF statement cross-check ไว้ให้ module ฐานข้อมูลบัญชีนี้)
- `module_other_income_key_features.md` — รายได้อื่นๆ: โครงสร้างเดียวกับ `module_expense` ทุกจุด (คนละทิศทางเงิน) ผู้ซื้อเลือกได้ทั้งผู้เช่าในระบบหรือ Contact ทั่วไป (บังคับเลือก), ใช้ Contact/Account/LedgerEntry ชุดเดียวกับค่าใช้จ่าย, เลขที่เอกสาร `INC-YYYY-MM-###`, หมวดหมู่ fixed 10 แบบ (ค่าปรับ/ค่าเช่าพื้นที่ส่วนกลาง/ดอกเบี้ยรับ/เงินมัดจำริบ ฯลฯ)
- `module_accounting_key_features.md` — ฐานข้อมูลบัญชี (module สุดท้ายในหมวดการเงิน): 4 แท็บ — ทะเบียนเอกสาร (7 sub-tab ดึงจาก module ต้นทางตรงๆ รวม "บิลรายวัน" ที่เพิ่มทีหลัง), บัญชีแยกประเภท (เลือกบัญชี ดูเดบิต/เครดิต/คงเหลือสะสม), จัดการบัญชี (`Account` — generalize มาจาก `BankAccount` เดิม ผู้ใช้เพิ่มเองได้ไม่จำกัด ลบได้เฉพาะยอด 0), ยอดค้างชำระ/ค้างรับ (2 ตารางแยก ไม่มี aging) — เพิ่ม `Deposit` entity ติดตามเงินมัดจำ (คืนเต็ม/ริบเต็มเท่านั้น ไม่มีริบบางส่วน, ริบแล้วสร้าง OtherIncome หมวด "เงินมัดจำริบ" อัตโนมัติ) — เพิ่ม `DailyBill` entity (บิลผู้เช่ารายวัน/walk-in, `DLY-YYYY-MM-###`, จ่ายล่วงหน้าเต็มจำนวนตอน check-in เสมอ, ไม่คิดค่าน้ำ-ไฟแยก, อยู่เกินออกบิลใหม่) **แก้จุดที่ module_bill ระบุไว้แต่สเปครอบแรกตกหล่น** — **ตัด requirement Bank Statement PDF cross-check ออกจากสโคป** เลื่อนไปทำทีหลัง — **แก้ไฟล์เดิม 4 ไฟล์ตามมา**: `module_bill`/`module_expense`/`module_other_income` (เปลี่ยน `bank_account_id`→`account_id`, `BankAccount`→`Account`) และ `module_contract` (เพิ่ม cross-reference ไปยัง `Deposit`, ไม่ต้องเพิ่ม field เพราะ `deposit_amount` มีอยู่แล้ว)
- `module_report_key_features.md` — รายงาน: ไม่มีภาพต้นแบบ ออกแบบเองทั้งหมด — หน้าสารบัญเดียว จัดกลุ่มลิงก์ตามหมวด (ไม่ใช่ tab) กด 1 รายงาน = เข้าเต็มหน้า, permission เดียวครอบทั้งโมดูล, ทุกรายงาน filter ช่วงวันที่ + export **Excel และ PDF (A4 แนวตั้ง)** แยกไฟล์ต่อรายงาน — 4 หมวด 17 รายงาน: **การเงิน 6** (สรุปรับ-จ่ายแยกหมวดหมู่, ค้างชำระ/Aging [ใช้ query เดียวกับฐานข้อมูลบัญชี], ยอดตามบัญชีที่รับเงิน, เงินสด-โอน, สรุปภาษี VAT/WHT, ยอดซื้อ-ขายตามคู่ค้า [เฉพาะ Contact ภายนอก]), **ห้องพัก 5** (สถานะห้องพัก/ผู้เช่า [snapshot ปัจจุบัน นับจากการเช่าจริง], เงินมัดจำ, มิเตอร์น้ำ-ไฟ [matrix แยกคอลัมน์น้ำ/ไฟต่อเดือน], occupancy rate [room-nights], การจอง), **ซ่อมบำรุง/พัสดุ 3** (แจ้งซ่อม, พัสดุ, ล้างแอร์/บำรุงรักษา), **ผู้เช่า 3** (รายชื่อผู้เช่า default active, สัญญาใกล้หมดอายุ ≤60 วัน, turnover) — ทุกรายงาน read-only ไม่เพิ่ม field/ตารางใหม่
- `module_setting_key_features.md` — ตั้งค่า: ไม่มีภาพต้นแบบ ออกแบบเองทั้งหมด — layout sidebar 7 หัวข้อ, ส่วนใหญ่แยกตามอาคาร ยกเว้น "ผู้ใช้งาน/สิทธิ์" ระดับบัญชีรวม — **ข้อมูลกิจการ/ผู้รับเงินรวมเป็นชุดเดียว** (เดิมมี 2 จุดอ้างอิงแยกจาก module_receipt กับ module_contract) ให้ทั้งคู่ดึงจากที่นี่, **ค่าตั้งสาขา** ครอบคลุมน้ำ/ไฟ/เน็ต/ส่วนกลาง/มัดจำ default ทั้งหมด (module_room อ้างอิงไว้), **ผู้ใช้งาน/สิทธิ์** เจ้าของสร้าง user ให้ staff ตรงๆ (ไม่มีอีเมลเชิญ), staff เข้าได้หลายอาคารผ่าน mapping table แต่ permission ชุดเดียวใช้ทุกอาคาร, permission ระดับ module (เปิด/ปิด ไม่ลงลึกถึง action), **ช่าง/ประเภทงานซ่อม/Template สัญญา** แยกตามอาคารทั้งหมด, **LINE OA** แยกตามอาคาร ตอนนี้เป็นแค่ placeholder — **จัดการอาคาร (CRUD) แยกเป็นหน้า Building Selector ต่างหาก ไม่อยู่ใน sidebar ตั้งค่า**
- `module_audit_key_features.md` — ประวัติการใช้งาน (Audit Log): **หน้ากลางอย่างเดียว ไม่มี per-entity view/export/click-detail** — owner-only, log เฉพาะ action สำคัญ 4 ประเภทต่อ module (สร้าง/ลบ/เงิน/เปลี่ยนสถานะ) ไม่ log การแก้ไข field ทั่วไป, มี system actor ชื่อตายตัว (`Auto checkout`, `ระบบ (ริบเงินมัดจำ)`) สำหรับ action ที่ระบบทำเอง, เก็บ `old_value`/`new_value` เป็น JSON ไว้ล่วงหน้าแต่ยังไม่มี UI แสดง diff, เก็บ log ถาวรไม่มี auto-purge — **แก้ไฟล์เดิมตามมา**: `module_room_key_features.md` ตัด Tab "ประวัติ" (แท็บที่ 7 ใน Room Detail Modal) ออกแล้ว เหลือ 6 tab เพราะยืนยันว่าไม่มี per-entity view
- `module_dashboard_key_features.md` — ภาพรวม (Dashboard, **module สุดท้ายในระบบ**): ไม่มีภาพต้นแบบ ออกแบบเองด้วย default ที่แนะนำทั้งหมด — ไม่มี data model ของตัวเอง เป็น consumer อย่างเดียว query จากทุก module, layout stat cards + กราฟ (`recharts`, รายรับ-รายจ่าย/occupancy 6 เดือนย้อนหลัง) + การ์ดรายการติดตาม (แจ้งซ่อมค้าง/พัสดุตกค้าง/สัญญาใกล้หมดอายุ) + activity feed จาก `AuditLog` (**owner only**), quick action 4 ปุ่ม reuse modal เดิมของ module ต้นทาง ไม่สร้างฟอร์มใหม่, ไม่ real-time (fetch ตอนโหลดหน้า), แสดงเฉพาะอาคารที่เลือกอยู่ไม่มีมุมมองรวมหลายอาคาร — **ข้อจำกัดสำคัญ:** ยังไม่มี module ไหน implement โค้ดจริงเลย ต้องมี Prisma schema ของ module ต้นทางอย่างน้อยบางส่วนก่อนถึงจะ query จริงได้ (หรือเริ่มด้วย mock data ไปก่อน)

## สถานะปัจจุบัน (หลังจบแชท module ประวัติการใช้งาน)
- **หมวดการเงินเสร็จสมบูรณ์ทั้งหมดแล้ว** — ไม่มี module ค้างในหมวดนี้อีก
- **module รายงาน (Reports) สเปคเสร็จแล้ว** — 4 หมวด **17 รายงาน** (การเงิน 6 [รวม VAT/WHT + ยอดตามคู่ค้า], ห้องพัก 5 [รวมมิเตอร์น้ำ-ไฟ + occupancy rate + การจอง], ซ่อมบำรุง/พัสดุ 3, ผู้เช่า 3 [รวม turnover]) ทุกรายงาน export ได้ทั้ง **Excel และ PDF (A4 แนวตั้ง)** ดู `module_report_key_features.md`
- **module ตั้งค่า (Settings) สเปคเสร็จแล้ว** — ปิดของค้างที่ module ฝั่งการเงิน/ห้องพัก/ผู้เช่า อ้างอิงไว้ทั้งหมด (role/permission, ข้อมูลกิจการ, ค่าตั้งสาขา, ช่าง, template สัญญา, LINE OA) ดู `module_setting_key_features.md`
- **module ประวัติการใช้งาน (Audit Log) สเปคเสร็จแล้ว** — หน้ากลาง owner-only, log เฉพาะ action สำคัญ ดู `module_audit_key_features.md` — **ทุก module ที่ implement โค้ดจริงต้องเรียกเขียน `AuditLog` ตอน action สำคัญสำเร็จด้วย** (ดูตารางในไฟล์นั้น)
- **ยังไม่มี module ไหน implement โค้ดจริงเลยสักตัว มีแต่สเปคครบทุกไฟล์** — ของเดิมในโปรเจกต์ (`app/rooms`, `app/bookings`) เป็นเวอร์ชันเก่ากว่าสเปคมาก (ดูหัวข้อด้านล่าง)
- **[แก้สเปคย้อนหลัง] module ห้องพัก (`module_room_key_features.md`) ตัด concept "โหมดปัจจุบัน/auto-switch" ออกแล้ว** — เปลี่ยนเป็น `rental_type_support` (รายวัน/รายเดือน/รายวัน+รายเดือน) ตอน setup ห้อง + derive ประเภทการเช่าปัจจุบันจาก Contract/Booking active แทน (ไม่เก็บ field แยกบน Room) — แก้ cross-reference ใน `module_bill_key_features.md` (ตาราง badge สถานะห้องบริบทบิล) ตามไปด้วยแล้ว — และตัด Tab "ประวัติ" ออกจาก Room Detail Modal แล้ว (ดูหัวข้อ module_audit ด้านบน)
- `Account` (เดิมชื่อ `BankAccount`) ย้ายจากหน้า "ตั้งค่า" มาจัดการที่ module ฐานข้อมูลบัญชีแล้ว — module "ตั้งค่า" ไม่มี CRUD บัญชีซ้ำ ยืนยันแล้วในสเปคตั้งค่า
- ระบบสิทธิ์ผู้ใช้งาน (role owner/staff + permission ระดับ module) ที่ module ฝั่งการเงินทุกตัวอ้างอิงไว้ — **ออกแบบสเปคเสร็จแล้วใน module ตั้งค่า** (permission ระดับ module เปิด/ปิด, staff เข้าได้หลายอาคาร permission ชุดเดียว) รอ implement โค้ดจริง
- "สื่อสาร" ถูกตัดออกจากรายการ module หลัก รวมเข้ากับ "ตั้งค่า" แล้ว (แค่ตั้งค่าเชื่อมต่อ LINE OA — ไม่มีระบบแชทในตัวระบบ)

## ✅ ครบทุก module แล้ว — ขั้นตอนถัดไปคือ implement โค้ดจริง

ทุก module (10 รายการในหัวข้อ "รายการ Module ทั้งหมด" ด้านบน) มีสเปคเสร็จหมดแล้ว **ไม่มี module ใหม่ให้ออกแบบสเปคอีก** ไฟล์ `next_module_prompt.md` นี้จึงไม่มี "module ถัดไป" ให้ตั้งเป้าหมายอีกต่อไป

**ก่อนเริ่ม implement จริง ควรตัดสินใจเรื่องเหล่านี้ (ยังไม่เคยตกลงกันไว้):**
- ลำดับการ implement module ไหนก่อน-หลัง (แนะนำ: เริ่มจาก Prisma schema รวมของทุก module ก่อน เพราะหลาย module cross-reference กัน เช่น Dashboard ต้องพึ่งเกือบทุก module)
- จะ implement ทีละ module แยกแชท เหมือนตอนทำสเปค หรือทำ schema รวมทีเดียวก่อนแล้วค่อยแยกหน้า UI ทีละโมดูล
- โค้ดเดิมใน `app/rooms`, `app/bookings`, `prisma/schema.prisma` (เวอร์ชันเก่าไม่ตรงสเปค) จะ rewrite ทับหรือลบทิ้งแล้วเริ่มใหม่

## หมายเหตุการใช้งาน prompt นี้
- แก้ "Module ที่กำลังทำในแชทนี้" และหัวข้อภาพ ให้ตรงกับ module จริงที่จะทำ
- ถ้าเปลี่ยนไปทำ module ที่ไม่เกี่ยวกับห้องพัก/ผู้เช่า/สัญญา/การเงินโดยตรง ตัดส่วนสรุปที่ไม่เกี่ยวออกได้ เก็บไว้แค่ส่วน Multi-Building ที่จำเป็นทุก module + ลิงก์ไปอ่านไฟล์สเปคที่เกี่ยวข้องในโฟลเดอร์นี้แทน
- หลังทำสเปค module ใหม่เสร็จในแต่ละแชท ให้สร้าง `module_xxx_key_features.md` ในโฟลเดอร์ `D:\ระบบ อพาร์มเม้นท์\code\ระบบ Aparment ลึก` (โฟลเดอร์นี้ ไม่ใช่ `D:\ระบบ Aparment ลึก` ที่ root ของ D:) แล้วอัปเดตไฟล์ `next_module_prompt.md` นี้ต่อ (mark ✅ module ที่เสร็จ + สรุปย่อผูกกับ module ถัดไป) เพื่อใช้เปิดแชทถัดไป
