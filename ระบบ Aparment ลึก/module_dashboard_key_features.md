# สเปค Module: ภาพรวม (Dashboard)

ไม่มีภาพต้นแบบ — ออกแบบเองทั้งหมดตามที่ตกลงกันในแชท (ใช้ default ที่แนะนำในทุกจุดที่ยังไม่ชัด เพราะ Dashboard เป็นหน้าที่คาดว่าจะปรับแก้เรื่อยๆ ไม่ต้อง lock สเปคแน่นเท่า module อื่น)

สถานะ: ✅ สเปคเสร็จ (รอ confirm ก่อน implement) — **module สุดท้ายในระบบ ครบทุก module แล้วหลังจากนี้**

---

## 1. หน้าที่ของโมดูล

หน้าแรกหลัง login (หรือหลังเลือกอาคารจาก Building Selector) — สรุปภาพรวมของอาคารที่กำลังเลือกอยู่ ดึงข้อมูลจริงจากทุก module ที่มีอยู่ (ไม่มี data model ของตัวเอง ไม่ generate ข้อมูลใหม่ เป็นแค่ query/aggregate หน้าจอเดียว)

**ขอบเขต multi-building:** แสดงเฉพาะอาคารที่กำลังเลือกอยู่ เหมือน module อื่นทุกตัว — **ไม่มีมุมมองสรุปรวมทุกอาคาร** ในรอบนี้ (เจ้าของที่มีหลายอาคารต้องสลับอาคารเพื่อดู dashboard ของแต่ละอาคารแยกกัน) — เหตุผล: รักษาความสอดคล้องกับสถาปัตยกรรมที่ตัดสินใจไว้ทั้งระบบ ลด complexity ของ query ข้ามอาคาร

## 2. Data Model

**ไม่มี** — query ตรงจาก Prisma model ของแต่ละ module ที่มีสเปคแล้ว: `Room`, `Bill`/`Payment`, `Tenant`/`Contract`, `RepairRequest`, `Parcel`, `AuditLog`, `Deposit` ฯลฯ

## 3. Layout หน้าจอ

Header: "ภาพรวม" + subtitle "สรุปข้อมูลสาขา [ชื่ออาคาร]" + วันที่ปัจจุบัน

### Section 1 — Stat cards แถวบน
- ห้องทั้งหมด / ห้องว่าง / มีผู้เช่า / Occupancy rate (%)
- รายรับเดือนนี้ (บาท) — sum `Payment` + `OtherIncomePayment` ของเดือนปัจจุบัน
- รายจ่ายเดือนนี้ (บาท) — sum `ExpensePayment` ของเดือนปัจจุบัน
- บิลค้างชำระ — จำนวนใบ + ยอดรวม (`Bill.status != paid`)

### Section 2 — กราฟ (ใช้ library `recharts`)
- กราฟเส้น/แท่งเทียบ 2 เส้น: รายรับ vs รายจ่าย ย้อนหลัง 6 เดือน
- กราฟ Occupancy rate ย้อนหลัง 6 เดือน (room-nights ต่อเดือน)

### Section 3 — รายการที่ต้องติดตาม (การ์ดย่อยเรียงข้างกัน 2-3 คอลัมน์)
- **งานแจ้งซ่อมค้าง** — 5 รายการล่าสุดที่ยังไม่เสร็จ + ปุ่ม "ดูทั้งหมด" ไปหน้าแจ้งซ่อม
- **พัสดุตกค้าง** — 5 รายการล่าสุด + ปุ่ม "ดูทั้งหมด" ไปหน้าพัสดุ
- **สัญญาใกล้หมดอายุ** (≤60 วัน, ใช้ query เดียวกับรายงาน) — 5 รายการ + ปุ่ม "ดูทั้งหมด" ไปหน้าผู้เช่า

### Section 4 — กิจกรรมล่าสุด (Activity feed)
- ดึง 5-10 รายการล่าสุดจาก `AuditLog` มาแสดงย่อ (ไอคอน + description + เวลา relative) + ปุ่ม "ดูทั้งหมด" ไปหน้าประวัติการใช้งาน
- **แสดงเฉพาะ owner** — สอดคล้องกับ permission ของ `module_audit` ที่ล็อกไว้ owner-only, staff ไม่เห็น section นี้เลย (ซ่อนทั้ง section ไม่ใช่แค่ disable)

## 4. Quick Actions

ปุ่มลัดในหน้า Dashboard (มุมบนหรือ floating) — กดแล้วเปิด modal เดิมที่ใช้ในหน้า module นั้นๆ (**reuse component เดิม ไม่สร้างฟอร์มซ้ำ**):
- "+ เพิ่มผู้เช่า"
- "+ บันทึกพัสดุ"
- "+ แจ้งซ่อม"
- "+ บันทึกค่าใช้จ่าย"

## 5. Real-time / Refresh

**ไม่ real-time** — fetch ข้อมูลตอนโหลดหน้าเท่านั้น (server-side ตอน request) ผู้ใช้ต้อง refresh หน้าเองถ้าต้องการข้อมูลล่าสุด — เหตุผล: ลด complexity ไม่ต้องทำ websocket/polling infrastructure เพิ่ม

## 6. Permission

- ทุก role (owner + staff) เข้าหน้านี้ได้ (เป็นหน้าแรกของระบบ)
- Section "กิจกรรมล่าสุด" (หัวข้อ 3 Section 4) แสดงเฉพาะ owner ตาม permission เดิมของ `module_audit`
- Quick action ที่ไม่มี permission module นั้น (เช่น staff ไม่มีสิทธิ์ "ค่าใช้จ่าย") → ซ่อนปุ่มนั้นออกจาก quick action ด้วย

## 7. ความสัมพันธ์กับ module อื่น

Dashboard เป็น **consumer อย่างเดียว** ไม่มี write operation ของตัวเอง (quick action เขียนผ่าน API ของ module ต้นทางโดยตรง):
- **ห้องพัก:** นับสถานะห้อง, occupancy rate
- **การเงิน (บิล/ค่าใช้จ่าย/รายได้อื่นๆ):** รายรับ-รายจ่ายเดือนนี้ + กราฟ 6 เดือน, บิลค้างชำระ
- **ผู้เช่า/สัญญา:** สัญญาใกล้หมดอายุ
- **แจ้งซ่อม/พัสดุ:** รายการค้าง
- **ประวัติการใช้งาน:** activity feed (owner only)

## ⚠️ ข้อจำกัดสำคัญก่อน implement จริง

**ยังไม่มี module ไหนในระบบ implement โค้ดจริงเลยสักตัว** (มีแต่สเปค `.md` ทุกไฟล์) — Dashboard ต้อง query ข้อมูลจริงจาก Prisma model ของทุก module ข้างต้น ซึ่งยังไม่มีอยู่ในโค้ดจริง (โค้ดเดิมใน `app/rooms`, `app/bookings`, `prisma/schema.prisma` เป็นเวอร์ชันเก่าที่ไม่ตรงสเปค)

**แนวทางแนะนำตอน implement:**
1. เขียน Prisma schema ของ module ที่ยังไม่มี (อย่างน้อย Room, Bill, Tenant, RepairRequest, Parcel, AuditLog) ให้ตรงสเปคก่อน — ไม่จำเป็นต้องมี UI ของ module นั้นครบ แค่ schema + seed ข้อมูลตัวอย่างพอให้ Dashboard query ได้จริง
2. หรือเริ่มจาก Dashboard UI/layout ด้วย mock data ไปก่อน แล้วค่อยสลับเป็น query จริงทีหลังเมื่อ module ต้นทางถูก implement ครบ

ต้องตัดสินใจแนวทางนี้ก่อนเริ่มโค้ดจริง (ดูคำถามท้ายไฟล์)

## หมายเหตุการดูแลรักษา
- โมดูลนี้ยังไม่ implement โค้ดจริง — รอ confirm ก่อนเริ่ม
- เป็น **module สุดท้ายที่เขียนสเปคครบ** — หลังจากนี้ไม่มี module ใหม่เหลือในสโคป ขั้นตอนถัดไปของโปรเจกต์คือเริ่ม implement โค้ดจริงตามสเปคทั้งหมด
